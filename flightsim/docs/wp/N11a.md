# N11a: Plan edits: the navigator rules and their tests

Phase 1.4 · Effort: high · Depends: none (never alongside N8, N10 or N11b: shared navigator) ·
Branch: `wp/N11a-plan-edit-rules`

## Why

The owner (2026-11-09) wants flight-plan changes to behave like a Garmin GTN / G1000 or an
airliner FMS: whatever changes, the aircraft keeps flying something sensible, and the pilot sees
one short message saying what happened. Today the edits are scattered and some are destructive
by accident: `directToWaypoint` (`FlightPlan.cpp`) drops every enroute leg and goes straight to
the plan tail; `deleteLeg` refuses the active leg's neighbours inconsistently; a new destination
can only be made by building a new plan; nothing can be undone. This card writes the rules as one
pure module with table-driven tests. N11b puts them on the screens.

## Do

1. **API** (`PlanEdit.h`, pure, allocation is fine: edits happen on a button press):
   ```cpp
   struct PlanEditContext { LatLon present; float trackTrueDeg = 0; float gsKt = 0; bool airborne = true; };
   struct PlanEditResult {
       bool ok = false; FlightPlan plan; std::string message; // "DIRECT TO SEA, THEN OLM"
       bool destructive = false; const char* undoLabel = "";  // "ROUTE REPLACED", "PLAN CLEARED"
   };
   PlanEditResult directTo(const FlightPlan&, const Waypoint& target, const PlanEditContext&);
   PlanEditResult directToNext(const FlightPlan&, const PlanEditContext&);
   PlanEditResult activateLeg(const FlightPlan&, int legIndex, const PlanEditContext&);
   PlanEditResult deleteWaypoint(const FlightPlan&, int legIndex, const PlanEditContext&);
   PlanEditResult changeDestination(const FlightPlan&, const Waypoint& airport, std::string_view runwayDb,
                                    bool keepRoute, const PlanEditContext&);
   PlanEditResult changeDepartureRunway(const FlightPlan&, const Waypoint& runwayStart,
                                        std::optional<std::vector<Leg>> sidLegsForNewRunway);
   ```
   SID / STAR / approach replacement keeps using `insertSid`, `insertStar` and
   `Navigator::loadApproach` (they already replace only their tagged legs); add a test row for
   each so the rule is pinned.
2. **Rules** (write them first as `docs/NAVIGATION.md` §2.4, then code them):
   1. *Direct-To a waypoint in the plan* (`legs[i].to`, i ≥ 1, not CA / VA): `[PPOS][DF i][legs
      after i]` as `directToLeg` does now. Earlier legs count as flown and go. Later constraints
      stay. `sidId` / `starId` are cleared when none of their legs is left. Message
      `DIRECT TO <X>`. Works the same inside the missed approach.
   2. *Direct-To a fix not in the plan* (X): rejoin at Y, the first waypoint from the active leg
      on whose turn at X (course PPOS→X to course X→Y) is ≤ 90°: `[PPOS][DF X][TF Y][rest after
      Y]`. Legs between the active leg and Y go (they were behind). No such Y: rejoin at the
      plan's tail (destination leg or the approach). Message `DIRECT TO X, THEN Y`.
   3. *Direct-To the destination* (its ident, when the plan has a STAR or an approach, so the
      destination leg is not in the plan): `[PPOS][DF <dest airport>]` followed by the STAR and
      approach legs, kept so they can still be flown. The navigator does not sequence past a DF
      leg to the destination airport (a new rule in `shouldSequence`); `reenterApproach` or a
      Direct-To a STAR / approach fix picks them up. Without a STAR or an approach, rule 1 on the
      destination leg. Message `DIRECT TO <DEST>`.
   4. *Direct-To another airport*: `[PPOS][DF <airport>]`, `destIdent` = it, `arrRunway`,
      STAR, approach and missed cleared. Destructive (`ROUTE REPLACED`). Message
      `DIRECT TO <APT>, ROUTE REPLACED`. N11b offers the new airport's approaches next.
   5. *New destination* (plan screen): the old destination's STAR, approach and missed approach
      always go. `keepRoute`: the origin, SID and enroute legs stay, the new destination leg
      (its runway threshold when `runwayDb` resolves, else the airport) replaces the old one; the
      active leg stays when it survives, else Direct-To the new destination. `!keepRoute`
      (default in N11b): `[PPOS][DF <airport>]`. Destructive either way (`ROUTE REPLACED` /
      `PLAN CLEARED`). Messages `NEW DEST <APT>, ROUTE KEPT` / `NEW DEST <APT>, ROUTE CLEARED`.
   6. *New departure runway* (on the ground): legs[0] becomes the new runway start; a SID is
      replaced by `sidLegsForNewRunway` when given, else removed (`SID <ID> REMOVED`). Nothing
      after the SID changes. New SID / STAR / approach: only their tagged legs change (the
      existing calls).
   7. *Delete the active waypoint* (or skip it): the next waypoint becomes active, direct from
      PPOS (`[PPOS][DF next][rest]`). Deleting another enroute waypoint: as `deleteLeg` does now.
      Approach legs are not deleted one by one (`USE CHANGE APPROACH`). Message
      `<X> DELETED, DIRECT TO <NEXT>` or `<X> DELETED`.
   8. *Direct-To next* (one press, after vectors or a heading excursion): Direct-To the active
      waypoint if it is still ahead (along-track distance to it on its leg > 0.5 NM, or the
      bearing to it within 90° of the track), else the first waypoint ahead. Message
      `DIRECT TO <X>`. *Activate leg* (i): make leg i active without a direct-to, so the
      navigator intercepts its course (`Navigator::activateLeg`). Message `ACTIVATE LEG <X>`.
   9. *Missed approach*: the MAP still sequences into the missed legs only when passed airborne
      (§3.4, unchanged). Direct-To during the missed approach follows rules 1–4.
3. **Undo** (in `Navigator`): `stashUndo(label, simTimeS)` keeps one copy of the plan before a
   destructive edit; `undoAvailable(simTimeS)` is true for 10 s; `undo(simTimeS)` restores it
   with `setPlan` and returns its label (message `<LABEL> UNDONE`). One level: a new destructive
   edit replaces it. N11b calls `stashUndo` before applying a destructive result.
4. **NAV continuity:** apply every result with `Navigator::setPlan` (never `clearPlan` then
   `setPlan`), so `NavState::activeLegIndex` stays ≥ 0 and the AP's `navAvailable` holds. VNAV
   and fly-by arcs (N10) rebuild from the plan signature as they do now; check them in the tests.
